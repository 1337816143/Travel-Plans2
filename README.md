# 全球旅行攻略（暂定）

> 从青岛单城市静态攻略升级为面向全球、支持 Web 与小程序的可扩展旅行规划平台。

## 项目定位

本项目不是把更多城市继续写进一个 HTML 文件，而是建立一套能够持续扩展的数据、规划、内容可信度和多端应用架构。

核心目标：

- 覆盖全球不同尺度的目的地：区县、城市、省州、流域/片区、国家、跨国线路及用户自定义区域；
- 聚合景点、打卡点、美食、购物、体验、公共服务、交通和住宿等多类地点；
- 同时保存“相对稳定的官方/编辑信息”和“有时效性的动态事实”；
- 在官方信息旁展示经过聚合与审核的社区反馈，并明确标注“来自旅行者反馈”；
- 提供强大的自定义选点、分组、标注、路线、备注、拖拽排程和自动重算能力；
- 为不同范围、旅行天数、预算、节奏和偏好生成可解释的预设或自定义行程；
- Web 与小程序功能保持一致，仅针对屏幕、导航和交互方式做适配，不以适配为由删减功能；
- 完整迁移并逐步增强原项目 `1337816143/travel-plans` 的已有能力。

## 架构原则

1. **领域模型优先**：地点、区域、来源、反馈、行程和地图标注均使用稳定的数据契约，不与某个页面绑定。
2. **供应商可替换**：高德、海外地图、天气、搜索和路线服务均通过适配器接入，避免核心业务锁定单一 API。
3. **事实有时效性**：营业时间、闭园、票价、施工、天气、交通等信息必须携带来源、采集时间、有效期和置信度。
4. **社区反馈不覆盖事实**：用户反馈作为独立信息层展示，达到阈值后显示在编辑信息旁，并保留“他人反馈”标识。
5. **规划可解释**：自动排程必须返回调整原因，例如营业时间冲突、通勤过长、天气风险或住宿位置不合理。
6. **多端功能同源**：领域逻辑、规划算法、API SDK、设计令牌和验收用例共享；Web 与小程序分别实现平台 UI 外壳。
7. **合规采集**：只使用开放数据、官方 API、明确授权的数据、合法公开资料和用户主动提交内容；不以绕过平台限制的方式抓取点评或社交平台数据。

## 目标工程结构

```text
Travel-Plans2/
├─ apps/
│  ├─ web/                 # Next.js Web/PWA，SEO、分享和大屏规划工作台
│  └─ miniapp/             # Taro 小程序，多平台构建与移动端交互
├─ services/
│  ├─ api/                 # 业务 API、鉴权、聚合查询和写入
│  ├─ ingestion/           # 数据接入、标准化、去重、更新和来源追踪
│  └─ planner-worker/      # 路线矩阵、自动排程、住宿分析和异步任务
├─ packages/
│  ├─ domain/              # 区域、地点、反馈、行程等领域模型
│  ├─ planner-engine/      # 与 UI、地图供应商无关的规划算法
│  ├─ provider-contracts/  # 地图、POI、天气、路线和内容源适配接口
│  ├─ api-client/          # Web/小程序共用 API SDK
│  ├─ design-tokens/       # 色彩、间距、字体、阴影和图标语义
│  └─ feature-contracts/   # 多端功能一致性清单与验收契约
├─ schemas/                # JSON Schema / 数据交换格式
├─ docs/                   # 架构、数据源、迁移和迭代文档
└─ infra/                  # 数据库、缓存、对象存储、队列和部署配置
```

## 核心领域

### 地理范围

- 行政范围：区县、地级市、省/州、国家；
- 自然与旅游范围：流域、海岛群、山地、海岸带、文化区、跨境走廊；
- 用户范围：地图框选、多边形、多个不连续目的地的集合。

### 地点类型

首批分类会覆盖：

- 观光：自然景观、历史文化、博物馆、美术馆、建筑、宗教场所、城市地标、观景点；
- 户外：徒步、露营、海滩、温泉、滑雪、潜水、骑行、公园与保护地；
- 娱乐：主题乐园、动物园、水族馆、演出、夜生活、赛事与节庆；
- 美食：正餐、小吃、早餐、甜品、咖啡、酒吧、夜市、菜市场、地方特产；
- 购物：必买、本地品牌、传统市场、商场、手工艺与伴手礼；
- 体验：课程、工坊、农事、游船、观光列车、导览与亲子项目；
- 住宿：酒店、民宿、青旅、度假村、营地与特殊住宿；
- 交通：机场、车站、港口、公交、停车、租车、充电与换乘点；
- 公共服务：厕所、医疗、警务、游客中心、行李寄存、无障碍设施与应急避难。

分类采用可扩展层级编码，不把中文显示名称直接写入业务判断。

## 数据可信度模型

每条动态信息至少包含：

- 对象与字段；
- 原始来源及来源类型；
- 采集/提交时间；
- 适用时间与过期时间；
- 地理位置或对象匹配证据；
- 自动置信度；
- 审核状态；
- 与其他来源的一致性或冲突关系。

社区反馈达到展示阈值后，以独立卡片显示：

> **旅行者反馈** · 近 30 天有 18 人提到东门临时关闭。最后反馈：2026-07-30。

它不会静默覆盖官方开放时间；当官方来源也确认后，才升级为编辑事实。

## 自定义规划能力

- 地图搜索、点击、框选、批量导入和从预设攻略加入地点；
- 为地点选择多套类别图标、颜色、大小、编号和显示层级；
- 自动生成缩放后仍可辨识的日序号/站点序号；
- 自定义备注、停留时间、预约时间、优先级、预算和同行人需求；
- 路线可选择交通方式、线型、粗细、箭头、方向、颜色语义和是否闭合；
- 地点、路线、备注和住宿可按“旅行/日期/城市/主题/成员”分组管理；
- 拖拽调整后局部重算，不无故破坏用户已锁定的安排；
- 自动检查营业时间、预约、天气、交通、时区、跨境和体力负担；
- 跨城市或跨国行程自动生成住宿分段、换城日和完整交通衔接方案；
- 每次自动调整都提供原因、替代方案和可撤销记录。

## 技术方向

- Web：Next.js App Router + React，兼顾 SEO、分享、PWA 和桌面规划工作台；
- 小程序：Taro + React，支持微信及后续其他小程序平台；
- 核心代码：TypeScript monorepo；
- 数据库：PostgreSQL + PostGIS；
- 缓存/队列：Redis；
- 文件与证据快照：兼容 S3 的对象存储；
- 数据更新：定时任务 + 事件驱动任务；
- 搜索：先使用 PostgreSQL 全文检索和地理检索，规模需要时再引入独立搜索引擎；
- 部署：容器化，环境配置与供应商密钥完全外置。

## 与旧项目的关系

旧项目不会直接作为新项目底座继续堆叠。迁移遵循：

1. 盘点旧功能及数据；
2. 将青岛地点、路线、主题和交互转换为新领域模型；
3. 建立功能对照测试；
4. 新架构实现同等能力；
5. 通过后再逐项增强并替换旧页面。

原项目中的地图、地点检索、愿望清单、路线展示、打印/分享、主题切换、响应式布局和多设备回归检查都属于迁移范围。

## 开发约束

- 密钥不得写入仓库或前端源码；
- 所有外部数据必须保留来源与许可证信息；
- 不允许由单一第三方平台的私有字段成为核心主键；
- 规划结果不得伪装成实时事实；
- Web 与小程序新增功能必须同时登记在功能契约中；
- 对地点事实的修改必须可追踪、可回滚。

## 许可证

项目许可证将在数据源和商业化边界确认后单独确定。引入任何第三方数据前，必须先记录其许可证、署名要求、缓存限制和再分发条件。
